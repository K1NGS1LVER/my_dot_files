# Best Local GGUF Model + Manual Install for M2 MacBook Air (16 GB, fanless)

> **For Hermes:** Use subagent-driven-development skill to implement this plan task-by-task.

**Goal:** Pick the best quantized GGUF model for this specific hardware (Apple M2, 16 GB unified, 8 GPU cores, passive/fanless) that (a) has a large context window, (b) does not thermally throttle the laptop, (c) exposes an OpenAI-compatible API so other agent harnesses can use it with high token limits — then give exact manual install steps.

**Architecture:** Continue using the existing `llama-server` (brew llama.cpp 10180) LaunchAgent on port 8080, which already publishes an OpenAI-compatible `/v1` API that `OPENAI_BASE_URL` points harnesses at. Only the model file, context size, and the shell `ai` alias change. This is a config change, not code — verification is via `curl` against the live server, not unit tests.

**Tech Stack:** llama.cpp (`llama-server` / `llama-cli`), GGUF quantization, Hugging Face Hub (`-hf` lazy download or `huggingface-cli`), macOS LaunchAgent, OpenAI-compatible API consumers (OpenCode, Pi Code, any `/v1` client).

---

## Recommended model

**Qwen3-14B-Instruct — GGUF, `Q4_K_M` quant.**

HF repo / `-hf` tag: `Qwen/Qwen3-14B-GGUF:Q4_K_M`

Why this is the best fit for *this* machine:

| Factor | Qwen3-14B-Instruct Q4_K_M | Qwen3-Coder-30B-A3B Q3_K_M (the "max coder" alt) |
|---|---|---|
| Weights size | ~9.3 GB | ~15.2 GB |
| Free RAM after load (16 GB − weights − ~2.5 GB OS/llama.cpp) | ~4+ GB for KV cache | ~0–1 GB — no room for context |
| Max comfortable context | 32K–64K (or 128K at Q3) | barely 8K before swap |
| Thermal load on passive M2 | moderate, sustainable | heavy, will throttle + fanless = sustained slowdown |
| Native context window | 128K | 262K (theoretical only — won't fit) |
| Agent / tool-calling quality | strong (Qwen3 Instruct) | best-in-class coder, but unusable here at size |
| Fits 16 GB with big context? | **yes** | **no** |

Qwen3-14B-Instruct is a strong general+both-coding model with native 128K context, good tool/function-calling for agent harnesses, and it's the largest model that fits 16 GB *with meaningful context headroom*. That directly satisfies "big context window" + "doesn't throttle too much" + "usable by other harnesses with high token limits."

**Edge-case alternative (only if you want max coding power and accept tradeoffs):** `Qwen/Qwen3-Coder-30B-A3B-Instruct-GGUF:Q3_K_M`. It will load on 16 GB but leaves almost no KV-cache room, so you must cap context low (~8K) and it will run hotter/slower on the fanless M2. Recommended ONLY if you drop the "big context" requirement. Not the default here.

## Step-by-step manual install

> You run the download yourself when ready. None of these steps download anything on their own except the explicit `huggingface-cli` / `-hf` commands you choose to execute.

### Task 1: Decide model + quant (done — see recommendation above)

- Primary: `Qwen/Qwen3-14B-GGUF:Q4_K_M`
- If you later want the coder alt: `Qwen/Qwen3-Coder-30B-A3B-Instruct-GGUF:Q3_K_M` (with ctx capped to 8192).

### Task 2: Download the GGUF into `~/models`

Pick ONE download method.

**Method A — lazy download via llama-server (simplest):** you don't pre-download; the first `launchctl start` in Task 5 pulls it automatically to the llama.cpp cache and serves it. No manual step needed. Skip to Task 3.

**Method B — explicit download with huggingface-cli (recommended if you want the file in `~/models`):**

```bash
cd ~/models
# install CLI if missing
brew install huggingface-cli 2>/dev/null || pip install -U "huggingface_hub[cli]"
# download the exact quant
huggingface-cli download Qwen/Qwen3-14B-GGUF Qwen3-14B-Q4_K_M.gguf --local-dir ~/models --local-dir-use-symlinks False
```

After this, verify the file exists:

```bash
ls -lh ~/models/Qwen3-14B-Q4_K_M.gguf
# expected: a ~9.3G file
```

If `huggingface-cli` errors, fall back to Method A (let llama-server fetch it by `-hf` tag).

### Task 3: Update the LaunchAgent plist

Stop the old server first so the port frees:

```bash
launchctl stop com.dan.llama-server
```

Edit `~/Library/LaunchAgents/com.dan.llama-server.plist`. Replace the `ProgramArguments` array so it reads:

```xml
<key>ProgramArguments</key>
<array>
    <string>/opt/homebrew/bin/llama-server</string>
    <string>-hf</string>
    <string>Qwen/Qwen3-14B-GGUF:Q4_K_M</string>
    <string>--n-gpu-layers</string>
    <string>99</string>
    <string>--no-mmap</string>
    <string>--mlock</string>
    <string>--flash-attn</string>
    <string>on</string>
    <string>-c</string>
    <string>65536</string>
    <string>--port</string>
    <string>8080</string>
</array>
```

Notes:
- `-c 65536` = 64K context. Drops to `-c 32768` if you see memory pressure / the server refuses to start with OOM. 128K is possible only at Q3_K_M and will be slower + hotter.
- `--flash-attn on` lowers KV-cache memory and speeds decoding on Apple Silicon — keep it.
- Keep `--no-mmap --mlock` (your existing thermal/pinning flags).

If you used Method B (file in `~/models`), you may instead point `-m` at the local path and drop `-hf`:

```xml
    <string>-m</string>
    <string>/Users/dan/models/Qwen3-14B-Q4_K_M.gguf</string>
```

### Task 4: Update the `ai` shell alias

In `/Users/dan/dotfiles/shell/shared/aliases.zsh` (currently line ~65), change:

```zsh
alias ai='cd ~/models && llama-cli -hf Qwen/Qwen2.5-Coder-7B-Instruct-GGUF:Q4_K_M --n-gpu-layers 99 --no-mmap --mlock -c 8192 -p "You are a helpful assistant."'
```

to:

```zsh
alias ai='cd ~/models && llama-cli -hf Qwen/Qwen3-14B-GGUF:Q4_K_M --n-gpu-layers 99 --no-mmap --mlock --flash-attn on -c 32768 -p "You are a helpful assistant."'
```

(Interactive `ai` uses a smaller 32K context to keep the chat snappy; the server uses 64K for agents.)

Also check `/Users/dan/dotfiles/shell/shared/aliases.nu` for an equivalent `ai` def and update it the same way if present (the `def` form, with `;` separators). If it's not there, skip.

### Task 5: Reload the LaunchAgent and start the server

```bash
launchctl unload ~/Library/LaunchAgents/com.dan.llama-server.plist 2>/dev/null
launchctl load ~/Library/LaunchAgents/com.dan.llama-server.plist
launchctl start com.dan.llama-server
```

Watch the log until it prints the listen line (first launch downloads the model, so allow a few minutes):

```bash
tail -f /opt/homebrew/var/log/llama-server.log
# expected eventually: "llama-server listening on http://127.0.0.1:8080"
```

### Task 6: Verify the server + model

In a separate terminal:

```bash
# 1) model is served
curl -s http://127.0.0.1:8080/v1/models | python3 -m json.tool
# expected: id contains "Qwen3-14B" / the -hf alias

# 2) a chat completion works (proves tokenizer + weights + API)
curl -s http://127.0.0.1:8080/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model":"local","messages":[{"role":"user","content":"Say hi in 5 words."}],"max_tokens":32}' \
  | python3 -m json.tool
# expected: a "choices" array with non-empty "content"

# 3) check context size actually applied
grep -i "ctx_size\|context" /opt/homebrew/var/log/llama-server.log | head
# expected: "ctx_size = 65536" (or whatever -c you set)
```

### Task 7: Point agent harnesses at the high context

Your harnesses already hit `OPENAI_BASE_URL=http://127.0.0.1:8080/v1`. The remaining step is to tell each harness the *context window* it may use (they otherwise default low, e.g. 8K/16K):

- **OpenCode / Pi Code:** set the model's `context_window` / `max_tokens` to ~64000 in their model config (Pi Code: `~/.pi/agent/models.json`; OpenCode: its provider/model settings). The server will honor up to the `-c` you set.
- **Generic OpenAI clients:** pass `max_tokens` up to ~64000 and rely on the server's 64K ctx.
- **jcode:** unchanged — it uses Ollama, not llama-server (see CHEATSHEET). If you want jcode on this model too, you'd have to add it to Ollama (`ollama pull qwen3:14b` or a custom Modelfile) — out of scope here.

## Risks, tradeoffs, open questions

- **Memory ceiling is hard.** 16 GB is the binding constraint. If the server fails to start with OOM, immediately drop `-c` to `32768`; if still OOM, drop to `Q3_K_M`. The 30B MoE will NOT work here with big context — don't fight it.
- **Thermal:** even 14B Q4 will warm a fanless M2 under sustained agent loads. `--flash-attn on` + capped context mitigate but don't eliminate. If you regularly do long agent runs, consider a cooling pad or accept lower context.
- **`--flash-attn` requires a llama.cpp build with flash attention; brew's 10180 should have it, but if the server rejects `--flash-attn`, remove that line (you lose some speed/memory efficiency, not correctness).
- **Context vs. quality:** running 128K at Q4_K_M may slightly degrade long-context recall vs. Q3; Q4_K_M is the better default for quality-at-size.
- **Harness token limits:** some harnesses hard-cap `max_tokens` regardless of server ctx. If a harness truncates, that's a harness setting, not the model — raise it in the harness config.
- **Open questions:** Do you want me to also wire the 30B coder MoE into Ollama for jcode (separate, bigger machine helper)? Do you want the llama-server plist added to the dotfiles repo manifest so it's tracked/symlinked like the ollama one?
